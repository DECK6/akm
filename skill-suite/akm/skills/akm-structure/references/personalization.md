# 공개 AKM을 사용자에게 맞게 구성하기

공개 [DECK6/akm](https://github.com/DECK6/akm)는 상위 AKM 스킬 묶음의 **지식 구조 기반 모듈**이다. [원본 스냅샷](../assets/upstream-akm/README.md)과 [출처·해시](../assets/upstream-manifest.json)를 필요한 범위만 읽는다. 전체 레이어를 모든 사용자에게 그대로 복사하지 않는다.

## 인터뷰에서 설계 결정으로

“인박스가 필요하세요?”라는 취향 조사로 끝내지 않는다. 사용자 분야의 실제 자료 흐름과 에이전트에게 맡길 일을 파고들고, 그 답에서 왜 필요한지 도출한다.

| 설계 축 | 분야별로 깊이 물을 것 | 선택과 영향 |
|---|---|---|
| 인박스 | 자료가 얼마나 자주 어디서 오는가, 읽기 전에 쌓이는가, 분류를 미루는 이유와 놓친 경험은 무엇인가 | inbox / 즉시 분류; 미분류를 추적할 방법까지 정한다 |
| 원문 | 다시 확인할 자료는 무엇인가, 원본은 어디 있는가, 출처가 사라지면 무엇이 곤란한가 | source층 / 외부 원문 위치와 근거 장부 |
| 지식 깊이 | 참고·개념 비교·여러 근거 합성 중 무엇이 필요한가, 반복 질문은 무엇인가 | reference / linked / synthesis; 노트 유형·관계 깊이 |
| 맥락 | 사람·팀·프로젝트·시점에 따라 달라지는 조건은 무엇인가 | context층 / 작은 도메인 프로필 |
| 기억 | 매번 다시 알려주는 규칙과 시작 전에 꼭 알아야 하는 것은 무엇인가 | memory 생략 / 짧은 포인터 |
| 절차 | 답변 외에 반복 실행할 일이 있는가, 순서가 결과에 영향을 주는가 | procedure 생략 / 작업별 절차 |
| 실행 기록 | 어떤 실패를 복구해야 하는가, 재현에 필요한 것과 기록할 필요 없는 것은 무엇인가 | action 생략 / 필요한 실행·결정만 기록 |
| 평가 | 틀린 답이나 실행을 어떻게 알아채는가, 손실과 반복 검증 기준은 무엇인가 | 노트 내 검증 / 전용 evaluation층 |
| 출력·보관 | 누구에게 무엇을 전달하는가, 오래된 설명을 다시 볼 필요가 있는가 | output/archive층 / 기존 보존 방식 |

답에서 나온 모순과 예외를 다음 질문 묶음으로 연결한다. 사용자가 더 꺼낼 내용이 없거나 구성을 정해 달라고 할 때까지 탐색하되 발견실에서 답한 내용을 반복하지 않는다. 사용자 선택이나 위임 없이 기본 7층을 확정하지 않는다.

## 구성안

권장안에 포함·생략·나중에 추가할 구성과 이유를 적는다. 다른 구성이 실제로 다른 효용/부담을 만들 때 비교한다. 지식 중심, 보조 운영, 실행 운영은 예시이며 자동 패키지나 등급이 아니다.

- evaluation 폴더를 생략해도 주장별 근거·검증 상태·정정은 남긴다.
- source층을 생략해도 원위치와 읽은 범위를 추적한다. 원문을 버리고 LLM 요약만 남기지 않는다.
- context층을 생략하면 도메인 목적은 시스템의 도메인 제어 문서에 둔다. 개인 사정을 공통 지식으로 섞지 않는다.
- memory·procedure·action층 없이도 작은 상태로 대화를 재개할 수 있다.
- inbox를 생략하면 즉시 분류한다. 미분류 항목은 대화/상태에 위치와 질문을 남기며 다른 이름의 숨은 inbox를 강제하지 않는다.

기존 공간은 현재 지침과 이번에 허용한 변경 범위를 따른다. 새 프로필을 만들었다는 이유로 기존 폴더·원문·규칙을 자동 이동/삭제하지 않는다. 경로·참조의 변경 계획과 복원 근거를 확보한 뒤 작은 단위로 이행한다.

## PROFILE.json

필드 구조는 [가상 예제](profile-example.json)를 참고한다. 예제를 실제 사용자 정보로 복사하지 않는다.

- `inbox`: true/false.
- `layers`: sources, knowledge, context, memory, procedures, actions, evaluation, outputs, archive 중 필요한 전용층.
- `knowledge_depth`: none, reference, linked, synthesis. knowledge층이 없으면 none.
- `operating_depth`: none(읽기/설명), assist(작업 보조), execute(실행·검증·학습). 실제 활성층은 layers에서 별도로 정한다.
- `decisions`: component, choice, reason, basis. 사용자 결정은 user-stated, 위임받은 추천은 llm-proposed. 중요한 구성별로 실제 답/위임과 포함·생략 이유를 남긴다.
- `pending_questions`: 아직 결정하지 못한 것. 미응답을 사용자 승인으로 바꾸지 않는다.

## 생성 도구

패키지 루트의 `scripts/workspace.py`는 선택한 폴더와 시스템 제어 문서만 만든다. 경로는 이 스킬의 실제 디렉터리에서 `../../scripts/workspace.py`다. 설치 링크를 쓰면 먼저 실제 경로를 해석한다.

```sh
python3 <package>/scripts/workspace.py plan --profile <profile.json> --root <new-workspace>
python3 <package>/scripts/workspace.py init --profile <profile.json> --root <new-workspace>
```

plan은 읽기 전용, init은 존재하지 않는 새 경로 전용이다. 기존 공간은 plan의 차이를 검토하고 별도로 이행한다. 생성 후 실제 인터뷰 기록·종료 상태를 이행하고 온톨로지·위키를 작성한다. 폴더 생성만으로 구축 완료를 주장하지 않는다.

## 공개 코어 이어 쓰기

스냅샷에는 공개 AKM의 시스템 규약·템플릿·어댑터·검사·내보내기 도구가 포함된다. **참고용 기반**이며 스냅샷 안의 AGENTS.md·ROUTER가 사용자의 맞춤 프로필을 자동으로 덮어쓰지 않는다. 원문은 수정하지 않는다.

원본 lint가 전체 레이어를 전제하는지 확인하고, 맞춤형 구성에서 생략한 층을 오류로 간주해 강제 생성하지 않는다. 기본 코어와 맞춤 프로필의 차이를 기록한다. 다른 에이전트 어댑터는 사용자가 지정한 경우 실제 경로에 맞게 연결한다.

상위 스킬 묶음과 공개 코어의 버전은 별도로 기록한다. 스냅샷 갱신은 변경점과 프로필 호환성을 검토하는 작업이며 자동 덮어쓰기가 아니다.
