# 온톨로지와 위키의 연결된 지식 계약

온톨로지와 위키는 **하나의 지식을 의미 모델과 설명문으로 표현**한다. 같은 폴더에 두거나 서로 링크 하나씩 넣는 것만으로 연결됐다고 하지 않는다. 이 규약은 ontology, wiki, ingest, query, review, grow, learn 역할에 공통 적용한다.

## 하나의 정본, 두 표현

| 대상 | 정본과 연결 규칙 |
|---|---|
| 질문 Q | 유래, 기대 답, 적용 조건, 답하면 안 되는 경우를 기록한다. 이를 competency question으로 삼는다. |
| 개념/대상 C | 안정 ID와 정본 정의 위치를 한 곳에 둔다. 위키는 같은 ID를 참조하며 별도 정의를 몰래 만들지 않는다. |
| 관계 R / 주장 A | R은 관계의 뜻, A는 실제 대상·조건·시점·근거다. 위키의 핵심 주장을 대응하는 A 또는 명시적 해석에 연결한다. |
| 노트 N | Q를 설명하며 사용한 C/R/A와 S의 위치를 남긴다. 모델 쪽에서도 이를 설명하는 N을 찾을 수 있어야 한다. |
| 출처 S | 원문 위치, 읽은 절/페이지/대화 발췌, 버전·날짜, 근거 성격을 함께 유지한다. 같은 원문을 여러 가짜 출처로 복제하지 않는다. |

`Q ↔ C/R/A ↔ N ↔ S`의 대응을 도메인 색인 또는 상태의 매핑에 둔다. 각 모델 행에 노트 링크를 두거나 하나의 연결표를 정본으로 삼아도 된다. 양쪽에서 찾을 수 있으면 되며 중복된 연결표를 의무화하지 않는다. **주요 결론은 출처 이름 목록만이 아니라 어떤 주장을 어느 구절이 지지하는지 추적 가능해야 한다.**

명시된 규칙과 그 규칙의 시점/예외에 대한 LLM 해석을 하나의 A-ID에 섞어 같은 근거 등급을 주지 않는다. 둘을 분리하고 해석이 기대는 원래 주장을 연결한다. 조건부 계산은 그 해석에 의존함을 본문에서도 드러낸다.

정본 정의를 모델에 둘지 위키의 정의 절에 둘지는 기존 환경에 맞춘다. 어느 쪽이든 위치를 명시하고 다른 표현이 이를 참조하게 한다. JSON, Markdown 표, RDF 등의 형식은 선택 사항이다. Markdown/JSON 모델을 OWL 또는 JSON-LD라고 부르지 않는다.

## 관계·조건을 잃지 않는 모델

- 분류(is-a), 부분(part-of), 사례(instance-of), 한때 맡은 역할을 구별한다. 폴더 레이어는 도메인 개념 종류가 아니다.
- 같은 이름은 동일성의 근거가 아니고 다른 이름도 별개 대상의 증거가 아니다. 별칭·ID 병합·분할에는 근거와 참조 보존이 필요하다.
- 부재는 기본적으로 미확인이다. 도메인에서 완결된 목록/규칙을 선언한 경우만 그 범위의 부정 판단에 쓴다.
- 비용·기간·권한·횟수 등이 함께 성립해야 하면 하나의 사건/규칙 ID나 조건 묶음으로 표현한다. 예를 들어 두 자원을 함께 소비하는 규칙을 각각의 자원만으로 충분하다는 두 독립 관계로 바꾸지 않는다.
- 관계의 방향·추이성·허용 종류는 명시한다. OWL을 채택하면 domain/range 추론과 입력 검증을 구별하고 검증 요구는 별도로 정의한다.
- 모델은 질문에서 검증할 약속이다. 질문 몇 개가 유일한 정답 모델을 자동 결정한다고 보지 않는다.

## 최초 구축

인터뷰에서 나온 질문에 필요한 작은 모델을 만들고 첫 3편을 작성하면서 부족한 정의·조건을 되돌려 보완한다. 모델 전체를 완성한 뒤에만 위키를 쓰는 선형 절차로 고정하지 않는다. 이미 좋은 용어체계가 있으면 재사용 범위를 검토한다.

위키 3편은 각기 답과 설명·적용 조건·근거·다른 노트 연결이 있는 실제 본문이다. 모델·색인·출처 장부는 편수에서 제외한다. 같은 Q를 보완적으로 나누는 것은 가능하지만 제목만 다른 중복 답은 만들지 않는다.

## 어느 쪽에서 시작해도 같은 변경 루프

사용자 정정, 새 자료, 모델 수정, 위키 문장의 모순은 모두 아래를 따른다.

1. 현재 정본을 다시 읽고 변경 근거 S와 이전 기준을 보존한다. 새 규칙인지 과거 서술의 오류인지 구별한다. 날짜가 최신이라는 이유만으로 권위를 높이지 않는다.
2. 바뀌는 C/R/A와 직접·간접 영향받는 N/Q·절차·색인을 찾는다. 이름 변경, 의미 변경, 적용 기간 변경을 구별한다.
3. 정본 정의/주장과 위키 설명·예제·계산·상호 링크를 함께 수정한다. 위키에서 발견한 새 구별도 모델에 반영한다. 원문 자체는 덮어쓰지 않는다.
4. 해소되지 않은 충돌은 근거 양쪽과 범위를 남긴다. 부분 반영이면 **실제 영향받는 노트와 색인**에 `needs-review`를 표시하고 상태에 미완료 대상을 기록한다. 전체 동기화 완료라고 하지 않는다.
5. 함께 검토한 모델 개정과 노트 개정/내용 해시를 `knowledge_revision` 또는 기존 버전 기록으로 묶는다. 이름만 붙이지 말고 이전 내용에 접근할 수 있는 변경 이력/사본을 남긴다.
6. INDEX·출처 장부·상태를 갱신한다. 검색을 실제 사용한다면 그 범위의 재색인과 재조회로 최신 정본이 회수되는지 확인한다. 검색 도구가 없으면 파일 탐색으로 검증하고 제한을 밝힌다.
7. 영향받은 질문을 다시 답하고 정상·반례·미확인 사례를 확인한다. 처음 3편은 유지하며 수정 때마다 3편을 추가하지 않는다.

수동 동기화도 가능하다. 도구가 여러 파일의 원자적 변경을 보장하지 않으면 그렇게 주장하지 않는다. 기존 사용자 지시가 승인/수정을 허용하면 추가 승인 절차를 발명하지 않는다.

## 답변과 검수

질문 범위/시점 → C의 의미 → A/R의 조건 → N의 설명 → S의 실제 구절을 필요한 만큼 따라간다. 답에는 결론·근거·적용 조건·빈틈을 제시한다. 내부 추론 전문을 출력할 필요는 없다.

자동 구조 검사, 의미적 정합성, 출처의 사실 지지, 실제 질문 효용은 별개다. 최소한 연결 누락/없는 ID, 근거 없는 관계, 조건을 생략한 답, 현재형으로 남은 폐기 주장, 모름을 거짓으로 해석한 답을 검수한다. 그래프가 연결됐다는 사실이나 모델의 자기평가를 정확성 보증으로 쓰지 않는다.
