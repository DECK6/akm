# 구축 이후의 지식 운영

AKM의 산출물은 계속 질문하고 수정할 수 있는 지식 공간이다. 역할 이름이 있다는 것만으로 운영이 되는 것은 아니다. 매 실행은 실제 입력, 변경 대상, 검증, 다음 작업으로 닫는다.

## 상태별 진입

| 상태/요청 | 실행 |
|---|---|
| 새 사용자·새 도메인 | discover → structure → ontology/wiki → query/lint/review |
| 새 분야를 기존 공간에 추가 | 그 분야의 discover → 기존 층에 도메인만 추가 → 초기 모델·위키 |
| 자료 하나가 들어옴 | ingest → 영향 대상의 ontology/wiki → connect → lint/review |
| 새 질문에 답하지 못함 | query에서 빈틈 식별 → 허용 시 explore/grow → 같은 질문 재조회 |
| 연결이 빠짐 | connect → lint → 질문 경로 재검증 |
| 완결성·건강 검사 | lint의 범위 검사 + review의 의미·질문 검사 |
| 알아서 확장·정비 | maintain이 정책과 예산 안에서 위 역할을 연속 실행 |
| 중단 후 재개 | context의 경로·revision·진행 작업부터 확인 |

자동 역할 전환이 임의 권한 확대를 의미하지 않는다. 조회만 요청받으면 답과 빈틈을 보여주고 저장하지 않는다. 확장·연결 보완을 맡겼으면 이미 위임한 파일 변경마다 승인을 반복하지 않는다.

## 운영 정책

상태의 `operations.policy` 또는 로컬 정책 파일에 실제 위임 범위를 기록한다. 기존 정책이 있으면 먼저 따른다. 새 자동 확장 요청에는 사용자가 범위를 이미 주었다면 질문 대신 한 사이클의 합리적인 한도를 알리고 실행할 수 있다. 예: 작업 3개, 새 출처 6개, 15분 중 먼저 도달하는 한도. 이는 변경 가능한 기본 예이며 지식량 목표가 아니다.

```json
{
  "mode": "maintain",
  "domain_ids": ["workshop"],
  "allowed_roles": ["akm-explore", "akm-ingest", "akm-grow", "akm-connect", "akm-lint", "akm-review"],
  "source_scope": {"local_roots": ["raw"], "web": false},
  "max_tasks": 3,
  "max_new_sources": 6,
  "max_minutes": 15,
  "requested_by": "실제 사용자 지시 또는 기존 위임 위치"
}
```

`mode`는 `advisory`(추천·검사), `maintain`(허용된 반영)으로 구별한다. `source_scope`는 실제 루트와 접근 가능한 자료로 채우며 예제의 raw를 강제하지 않는다. 외부 웹을 허용해도 사용자 비공개 내용을 검색어에 실어 보내는 허가는 아니다. 게시·삭제·스케줄 등록·유료 서비스 추가는 이 정책의 자동 확장에 포함되지 않는다.

전용 운영층 유무와 에이전트의 유지보수 위임은 별개다. 지식층만 사용해도 노트와 작은 상태 파일로 유지보수할 수 있다. 반대로 운영층이 존재한다는 이유로 자동 확장이 허가된 것은 아니다. 기존 프로필이 자동 실행을 명시적으로 금지했으면 새 사용자 지시의 적용 범위를 기록해 정책을 갱신한다.

## Backlog와 실행 상태

기존 `akm-state.json`을 확장한다. 오래된 상태에 새 필드가 없으면 비어 있는 것으로 읽되 과거 기록은 보존한다. 현재 상태만 간결하게 유지하고 필요한 과거 실행 근거는 기존 actions/evaluation 위치 또는 도메인 검증 기록으로 분리한다.

- 작업: `id`, `question_ids`, `target_ids`, `role`, `reason`, `needed_evidence`, `status`, `attempts`, `last_attempt_revision`.
- 상태: `pending → in-progress → verified | needs-review | blocked | no-change`. `verified`에는 실제 `changed_paths`, `changed_ids`, `revision`, `verification_paths`가 필요하다. 파일만 쓰고 검증하지 않았으면 `written` 단계로 기록한다.
- 사이클: `run_id`, `started_at`, `base_revision`, `policy`, `current_task_id`, `tasks_attempted`, `sources_read`, `checkpoint`, `stop_reason`, `next_action`.
- 초기 `initial_note_ids`는 고정한다. 새 노트는 `notes`에 추가하며 새 도메인은 자신의 최초 3편을 구별한다.

frontier의 stable task ID/대상/원인을 기존 backlog와 대조한다. 같은 개정에서 새 근거 없는 실패를 반복 실행하지 않는다. 새 자료·수정된 의존성·사용자 지시가 생기면 재개한다. 진행 중 에이전트가 바뀌어도 원문과 실제 파일부터 재확인한다. 실패한 생성물을 완료 노트로 세지 않는다.

한 도메인의 정본을 쓰는 작성자는 한 번에 하나다. 호스트의 작업 잠금 또는 Git 분기를 활용한다. 읽기/조사는 병렬 가능하지만 공유 모델·색인·상태의 반영은 직렬화한다. 시작 리비전과 현재 리비전이 다르면 기존 변경을 읽고 통합한 뒤 검증한다.

## 변경 단위

1. 바꿀 주장/정의/조건과 영향을 받을 N/Q를 읽고 변경 전 사본 또는 Git 기준을 확보한다.
2. 새 출처 S와 기존 사실을 구별하고 실제 C/R/A의 조건·상태를 갱신한다.
3. 관련 위키 본문·예제·질의 답·양방향 대응과 색인을 함께 갱신한다. 아직 반영 못 한 실제 노트에는 needs-review를 표시한다.
4. 실제 정본에서 검사 투영과 해시를 다시 만들고 lint → 질문 재조회 → 의미 검토를 수행한다.
5. 검증 결과가 있는 경우에만 공동 revision과 작업 완료를 기록한다. 실패 시 이전 지식을 조용히 파괴하지 않고 변경을 복구하거나 보류 상태를 드러낸다.

## 완결성의 의미

“분야의 모든 지식을 다 안다”는 종료 조건이 아니다. 브리프에 선언한 질문·범위·정상/반례/미확인 기준을 현재 근거로 만족하는지를 검사한다. 보고에는 다음을 따로 남긴다.

- 구조: ID·파일·종류·출처·연결표·갱신 상태.
- 질문: 답할 수 있는 질문, 못 답하는 질문, 범위 밖으로 보류한 질문.
- 의미: 관계의 뜻·조건·예외·출처 지지·모순, 실제 답의 일관성.
- 운영: 새 자료 반영·이전 질문 재검증·재개 가능성.

`complete_for_declared_scope`가 true여도 해시/검사 기록에 관한 기계 판정일 뿐이다. 사람이/에이전트가 정본과 실제 답을 확인한 결과를 `akm-review`가 별도로 기록해야 한다. 예산 소진은 완료가 아니며 `budget-exhausted`로 남긴다. 근거 부족은 `no-progress`나 해당 작업의 `blocked`다.

## LLM Wiki에서 온톨로지까지 확장

수집·합성·질의·린트·재편집 루프를 같은 Q/C/R/A/N/S로 확장한다. 기존 위키를 받아들일 때 폴더를 강제 변환하지 않는다. 주요 개념과 주장부터 최소 모델을 추출하고 기존 노트 ID·원문·조건을 유지한다. 큰 노트의 분할/중복 병합은 원문 요약 개수가 아니라 질문과 의미 경계를 기준으로 하고 대체 ID·링크·반례 검사를 함께 갱신한다.

연결 추천은 connect, 근거 탐색은 explore, 실제 편입은 ingest, 전체 조정은 maintain이 담당한다. 이 역할들은 첫 구축에서도 필요한 경우 호출되며 신규 분야와 기존 분야를 같은 고정 설문으로 다루지 않는다.
