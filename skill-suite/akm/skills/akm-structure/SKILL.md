# AKM Structure — 지식 분류와 운영 설계

[공통 계약](../akm/references/contract.md), [작업공간 규약](../akm/references/workspace.md), [맞춤 설계](references/personalization.md)를 읽는다. 공개 AKM은 기반 모듈이고 사용자의 인터뷰가 실제 구성을 정한다. **다음 자료를 어디에 놓고 어떻게 다시 쓸지 결정 가능하게 만드는 것**이 목적이다.

## 조사와 도메인 질문

신규 구축이면 [시작 라우팅](../akm/references/start-routing.md)에 따라 `akm-discover`를 먼저 읽고 실행한다. 이 스킬이 직접 로드돼도 폴더 생성부터 하지 않는다. 완료한 인터뷰의 인계나 명시적인 인터뷰 생략 지시가 있으면 그 상태부터 이어간다.

기존 지식 공간의 실제 파일, INDEX, 분류 규칙, 도메인 브리프를 읽는다. 빈 공간인지, 기존 구조를 유지하며 매핑할지 구분한다. 저장 위치가 불명확하고 실제 쓰기가 필요하면 위치를 확인한다.

자료 흐름이 불명확하면 실제 도메인을 기준으로 묶어 묻는다. 어떤 자료가 들어오는지, 무엇을 원문으로 보존하는지, 자주 다시 찾는 질문은 무엇인지, 개인 판단과 일반 지식을 어떻게 구분하는지, 실패를 어디에 남기는지 파고든다. 분야 전체의 탐색이 필요하면 `akm-discover`로 이어간다.

## 설계와 구축

1. 해당 사용자의 실제 자료·업무 예시를 저장 레이어에 대응시킨다. 도메인 전문용어를 폴더 계층과 혼동하지 않는다.
2. 인터뷰에서 인박스 유무, 지식의 깊이, 운영층의 범위를 결정하고 PROFILE.json에 이유와 근거를 남긴다. 신규 공간은 선택한 레이어와 시스템 문서만 만든다. 기존 환경이면 대응표와 변경 계획부터 작성한다.
3. 원문 보존, 새 입력의 inbox 또는 즉시 분류, 노트의 메타데이터·상태, 정본과 출력본의 구별, 보관/복원의 경계를 명시한다. 생략한 전용층의 기능을 어디까지 수행할지와 나중에 추가할 조건도 정한다.
4. 도메인 브리프·온톨로지·위키·출처 장부·검증 기록의 경로를 공통 상태에 등록한다. 아직 만들지 않은 결과는 예정 경로로 구분한다.
5. 실제 자료 예시를 분류해 보고 같은 자료가 여러 층에 걸치면 원문과 해석/맥락을 분리해 링크한다. 파일을 중복 복제하는 것으로 분류를 대신하지 않는다.

## 역할 경계

온톨로지의 개념 종류는 `akm-ontology`, 설명 노트의 내용은 `akm-wiki`가 맡는다. 여기서는 위치·수명·발견 가능성을 만든다. 긴 전문 지식을 memory에 넣지 않는다. 반복 절차만 procedure로, 개인 상황은 context로 둔다.

## 완료 조건

사용자의 새 자료·지식·운영 규칙·실패 예시를 각각 어디에 놓을지 실제 ROUTER로 판정할 수 있어야 한다. INDEX에서 도메인 정본을 찾고, 필수 메타데이터를 검사하고, 원문을 덮어쓰지 않았는지 읽어 확인한다. 경로 매핑과 남은 분류 쟁점을 인계한다.

기존 공간에 새 분야를 추가하면 전역 PROFILE/ROUTER와 기존 도메인을 보존한다. 생성된 공간에는 [작업공간 규약](../akm/references/workspace.md)의 domain-plan/domain-init을, 기존 커스텀 위키에는 수동 매핑을 사용한다. 해당 도메인의 INDEX 포인터와 인터뷰 근거까지 연결한 뒤 ontology/wiki로 넘긴다.
