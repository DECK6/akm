# AKM Ontology — 의미와 관계 설계

[공통 계약](../akm/references/contract.md)과 [연결된 지식 계약](../akm/references/linked-knowledge.md)을 읽고 도메인 브리프·탐색 지도·기존 모델·이번 질문을 확인한다. 신규 구축이면 [시작 라우팅](../akm/references/start-routing.md)에 따라 `akm-discover`부터 수행한다. 모든 분야에 사람·기관·프로젝트 구조를 강제하지 않는다.

## 설계 질문

분야에 맞는 개념 경계가 모호하면 관련 질문을 묶는다. 실제로 혼동하는 두 용어, 같은 이름인데 다른 대상, 결과를 바꾸는 조건, 예외 사례, 누가 어떤 상황에서 다르게 판단하는지 함께 파고든다. 사용자 답을 가설과 구별하며 상세 탐색은 `akm-discover`의 방식을 따른다.

## 모델 만들기

`ontology.md` 또는 기존 모델 형식에 다음을 작성한다. 초기 크기는 실제 질문을 표현하는 데 필요한 만큼 정하고 무의미한 분류를 늘리지 않는다.

| 구성 | 필요한 정보 |
|---|---|
| 도메인 | 범위·제외·목적·열린 전제 |
| 활용 질문 Q | 실제 질문, user/llm-recommended 유래, 기대 답, 적용 조건, 답하지 말아야 할 경우 |
| 대상 종류 T | 이름, 뜻, 포함/제외 사례 |
| 개념/대상 C | 표제어, 종류, concept/instance 구분, 정의, 별칭, 경계, 근거 |
| 관계 정의 R | 뜻, 방향, 시작/끝에 허용되는 종류, 성립 조건, 추론 제한 |
| 관계 주장 A | 시작 C, R, 끝 C, 조건/시기, S 근거, 근거 성격, 현재 상태 |

관계의 틀을 만들었다는 것과 그 관계가 실제로 성립한다는 것은 다르다. 주장에는 source-supported, user-stated, llm-proposed를 구분한다. 근거가 없는 가설은 지울 필요 없이 제안으로 유지한다. `current`는 사실 검증 등급이 아니다.

“함께 나타남”을 원인으로, 추천을 필수 조건으로, 부분을 하위 종류로 바꾸지 않는다. 대칭·역관계·추이성을 정의하지 않았으면 자동 추론하지 않는다. 별칭 추가와 개체 병합은 정의·범위·수준을 대조한 뒤 한다.

## 실제 질문에 대입

활용 질문 하나를 선택하고 어떤 C/R/A를 따라 무엇을 답할 수 있는지 설명한다. 관계 문장을 자연어로 읽어 사용자 표현과 대조한다. 답을 만들 수 없다면 부족한 관계인지 자료 부족인지 질문 범위의 문제인지 구분한다. 존재하지 않는 경로를 그려 답을 만들지 않는다.

## 수정과 인계

[평가 규약](../akm/references/evaluation.md)에 따라 정상·반례·미확인 사례를 시험한다. 알려진 용어체계가 있으면 필요한 범위의 재사용을 검토한다. 부재를 거짓으로, 관계 그래프의 연결을 사실 증명으로 취급하지 않는다. 위키 설명에서 새로 드러난 정의·조건을 모델로 되돌리고 양쪽에서 같은 ID를 찾게 한다.

기존 ID를 유지한다. 병합·분할·폐기 시 이전 ID와 대체 대상을 기록하고 참조를 갱신한다. 영향받는 위키 노트·질문을 찾아 함께 수정하거나 needs-review로 표시한다. 관련 노트에만 모델의 변화가 반영되도록 `akm-wiki`/`akm-grow`에 실제 변경 ID를 넘긴다.

완료 전 ID 중복·없는 끝점·종류 제약·출처 대응·모순을 확인한다. 형식 통과는 의미나 사실의 증명이 아니다. 개정 번호, 실제 검증한 질문, 미확인 관계를 공통 상태에 남긴다.

변경 전후 `akm-lint`의 impact·종류/참조 검사를 사용하고, 본문과 연결표가 다르면 정본에서 재추출한다. 빠진 대응과 탐색 연결은 `akm-connect`로 보완한다. 검사 도구가 확인하지 않는 역관계·추이·카디널리티·모순은 해당 모델 형식의 검증기 또는 직접 의미 검토로 확인한다.
