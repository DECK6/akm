# AKM Review — 지식 시스템 검수

[공통 계약](../akm/references/contract.md)을 읽는다. 요청 범위와 검토할 실제 개정본을 고정한다. 검토만 요청받으면 지적을 남기고 내용을 임의로 수정하지 않는다. 수정까지 요청받았으면 근거가 있는 오류를 교정하고 재검증한다.

먼저 `akm-lint`의 기계적 검사 결과를 읽고 정본·노트 본문·실제 답을 별도로 검토한다. [지속 운영](../akm/references/lifecycle.md)의 현재 질문 범위와 완결성 기준을 사용한다.

## 검토 관점

| 관점 | 확인할 것 |
|---|---|
| 분류/운영 | 원문 보존, knowledge/context/procedure 경계, 과도한 memory, INDEX에서 발견 가능성 |
| 의미 | 용어 정의, 개념/사례 구분, 관계의 방향·조건·허용 종류, 잘못된 인과/추이 추론 |
| 정합성 | 중복 ID, 없는 참조·파일, 폐기 ID, 서로 어긋나는 상태, 갱신되지 않은 관련 노트 |
| 근거 | 주요 주장과 실제 출처의 대응, 미독 인용, 순환 인용, 사용자 진술/LLM 가설의 혼동 |
| 시간/충돌 | 자료의 시점·버전·적용 범위, 반대 근거, 오래된 사실의 현재형 사용 |
| 효용 | 사용자 질문에 실제로 답할 수 있는지, 답을 바꿀 조건을 설명하는지 |
| 재개 | 다음 에이전트가 실제 파일·미확인·다음 작업을 찾아 이어갈 수 있는지 |

모든 도메인의 품질을 같은 체크리스트만으로 판단하지 않는다. 사용자가 실제로 실패를 구분하는 기준과 사례를 읽고 검사에 반영한다. 기준이 없다면 어떤 판단이 틀리면 곤란한지, 성공/실패 사례가 어떻게 다른지 묶어 확인한다.

## 지적 형식

실제 위치, 관찰한 현상, 영향을 받는 질문, 근거, 권장 수정, 재검증 방법을 남긴다. 가능성이 있다는 이유만으로 오류라고 하지 않는다. 확실하지 않으면 추가 확인 항목으로 둔다.

초기 구축에서는 지식 노트가 실제 3편인지 확인하고 제어 문서를 제외한다. 이후에는 3개 초과를 오류로 보지 않는다. 모든 초기 노트에 질문·답·의미 연결·근거와 한계가 있는지 본문을 읽는다.

## 교정과 검증

정의/관계의 오류는 `akm-ontology`, 설명/출처는 `akm-wiki`/`akm-ingest`, 저장 경계는 `akm-structure`, 반복 실패는 `akm-learn`에 연결한다. 실제로 바뀐 부분의 전후 근거를 남기고 영향을 받는 질문에 다시 답한다.

자동 검사나 LLM 자기검토만으로 사실 정확성을 보증하지 않는다. 구조 통과, 직접 확인한 주장, 실제 질문 사용 결과를 나눠 보고한다. 모든 영역을 검사하지 않았으면 검토한 범위를 명시한다. 의미 있는 결과를 환경의 evaluation 위치에 저장한다.

완결성 검토에서는 도메인 색인과 실제 파일 목록을 검사 연결표와 대조해 누락 노트를 찾는다. 선언한 핵심 질문마다 답 노트·사용한 관계·주장별 근거·정상/반례/미확인 결과를 연결한다. 의미 모순, 관계 방향/추이·카디널리티·적용 조건, 기존 정정의 전파는 본문/형식별 검증기로 직접 확인한다. 시험하지 않은 차원은 not-tested다. 질문이 없거나 린트 오류만 0인 상태를 완결로 보고하지 않는다.

결과는 구조 / 의미·근거 / 질문 / 운영 각각 pass, needs-review, not-tested와 근거 경로로 남긴다. 한 차원의 실패를 다른 좋은 지표로 상쇄하지 않는다. 연결 지적은 `akm-connect`, 조사 지적은 `akm-explore`, 실제 확장은 `akm-grow`로 넘기고 `akm-maintain`이 해결 또는 보류 상태까지 추적하게 한다.

[평가 규약](../akm/references/evaluation.md)에 따라 정상·반례·미확인 질문을 확인한다. 효과 비교를 요청받으면 같은 자료·질문의 원문/위키/위키+온톨로지 결과와 실제 검토 부담을 비교한다. 자료 추가 효과를 구조 개선 효과로, 합성 예를 실측 성과로 보고하지 않는다. 전용 evaluation층이 없으면 검증한 노트/상태에 필요한 기록을 남긴다.
